# 消息模式分类

消息中间件里，生产者与消费者之间如何传递消息，常见两大模式：**点对点（Queue）** 与 **发布订阅（Topic）**。二者的核心差异在于：**一条消息最终被几个消费者处理**。

***

### Peer-to-Peer（Queue，点对点 / 队列模式）

<div align="center">
    <img src=./消息模式分类1.jpg width=60% />
</div>

- **Producer** = 生产者：往队列里投递消息
- **Queue** = 队列：暂存消息的通道
- **Consumer** = 消费者：从队列中取消息并处理

**核心特征：**

1. **一对一消费**：一条消息只会被 **一个** 消费者拿走并处理（竞争消费 / Competing Consumers）。
2. **负载均衡**：多个消费者挂在同一队列上时，消息会在它们之间分摊，适合做任务分发。
3. **解耦**：生产者只认识队列，不关心谁在消费、有几个消费者。
4. **可堆积**：消费端忙不过来时，消息先在队列里排队，削峰填谷。

**典型场景：** 订单处理、异步任务、短信/邮件发送、日志入库等「做一次就够」的工作。

***

### Publish/Subscribe（Topic，发布订阅模式）

<div align="center">
    <img src=./消息模式分类2.jpg width=60% />
</div>

- **Publisher** = 发布者：往主题上发布消息
- **Topic** = 主题：消息的分类通道 / 广播中枢
- **Subscriber** = 订阅者：订阅某主题，接收该主题上的消息

**核心特征：**

1. **一对多广播**：一条消息会投递给 **所有** 当前订阅该主题的订阅者（每人一份副本）。
2. **按兴趣订阅**：订阅者只关心自己订阅的 Topic，发布者不需要知道有哪些订阅者。
3. **解耦更强**：发布端与订阅端在时间、空间、身份上都可以完全独立。
4. **侧重点不同**：强调「事件通知 / 状态同步」，而不是「任务只做一次」。

**典型场景：** 库存变更通知、缓存失效广播、配置下发、监控告警、多系统联动（下单后同时通知库存、积分、物流）。

***

### 常见中间件归属

| 中间件 | 点对点（Queue） | 发布订阅（Topic） | 说明 |
|--------|-----------------|-------------------|------|
| **ActiveMQ** | ✅ Queue | ✅ Topic | JMS 标准双模型，两种 Destination 原生支持 |
| **RabbitMQ** | ✅ 队列竞争消费 | ✅ Exchange 广播 | 以 Exchange + Queue 实现；Direct/默认交换机偏点对点，Fanout/Topic 交换机偏发布订阅 |
| **Kafka** | ✅ 同 Consumer Group | ✅ 多 Consumer Group | 对外统一是 Topic；组内竞争消费≈队列，多组各收一份≈发布订阅 |

要点：

- **ActiveMQ**：最「教科书」——明确区分 Queue / Topic 两种目的地。
- **RabbitMQ**：消息先到 **Exchange**，再按规则路由到 Queue；模式由交换机类型决定，而不是单独叫 Queue/Topic 两种产品。
- **Kafka**：只有 Topic，没有独立 Queue 概念；用 **Consumer Group** 同时覆盖两种语义。
