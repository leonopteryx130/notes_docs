# 指令重排

### CPU 流水线技术

抽象且简化地看，一条 CPU 指令的执行过程可以分成 4 个阶段：**取指、译码、执行、写回**。

这 4 个阶段分别由 4 个独立的物理执行单元完成。若指令之间没有依赖，后一条指令不必等前一条完全执行完再开始——前一条完成取指后，后一条就可以立刻开始取指。

比较理想的情况如下图：指令之间无依赖，流水线并行度最大。

<div align="center">
    <img src=./指令重排1.png width=80% />
</div>

按序执行时，一旦遇到指令依赖，流水线就会停滞。例如：

```text
指令 1: Load R3 <- R1(0)    # 从内存加载数据到 R3
指令 2: Add  R3 <- R3, R1   # 加法，依赖指令 1 的结果
指令 3: Sub  R1 <- R6, R7   # 减法
指令 4: Add  R4 <- R6, R8   # 加法
```

指令 2 依赖指令 1：指令 1 未完成前，指令 2 无法执行，流水线效率会明显下降。

<div align="center">
    <img src=./指令重排2.png width=80% />
</div>

指令 3、4 与其它指令无依赖，可以把它们「乱序」到指令 2 之前执行。

<div align="center">
    <img src=./指令重排3.png width=80% />
</div>

这样执行单元能尽量保持忙碌。通过乱序执行调整指令顺序，可以提高流水线效率，让指令尽可能并行。

### 指令重排是什么

**指令重排（Instruction Reordering）**：在不改变程序「可见语义」的前提下，调整指令的实际执行（或生成）顺序，以换取更好的性能。

常见发生在两个阶段：

| 阶段 | 谁在重排 | 说明 |
|------|----------|------|
| 编译期 | 编译器 | 源码 → 汇编/机器码时，按优化策略重排、合并、删除指令 |
| 运行期 | CPU | 乱序执行（Out-of-Order Execution），硬件动态调度指令 |

两者目标一致：在遵守依赖约束的前提下，让流水线/执行单元更充分利用。

#### 1. 编译器重排

编译器优化（如 `-O2`、`-O3`）时可能：

- 调整无关语句的先后顺序
- 把计算提到循环外、合并重复读写
- 删掉「看起来没用」的读写（死代码消除）

约束是 **as-if 规则**：对**单线程、符合语言标准**的程序，优化后对外可观察行为应与未优化时等价。  
多线程下，若线程间只靠普通共享变量同步、没有正确同步手段，编译器重排可能导致其它线程看到「乱序」的中间状态。

#### 2. CPU 运行时重排

现代 CPU 会乱序执行：只要数据依赖、控制依赖等允许，硬件可以把后面的独立指令提前发射。  
对单核、单线程来说，写回（提交）阶段仍会保证该线程看到的最终结果符合程序顺序；  
多核场景下，一个核上的写对其它核何时可见，还受**内存模型 / 缓存一致性**影响，可能出现「其它线程观察到的顺序」与源码顺序不一致。

### 举个例子（多线程）

写线程先写 `data`，再置 `flag = 1`；读线程看到 `flag == 1` 后认为 `data` 已就绪。两边都用普通 `int`，没有任何同步：

```c
#include <pthread.h>
#include <stdio.h>

int data = 0;
int flag = 0;   // 错误示范：应用 atomic / 锁，这里故意不用

void *writer(void *arg) {
    data = 42;   // ① 先准备数据
    flag = 1;    // ② 再发「就绪」信号
    return NULL;
}

void *reader(void *arg) {
    while (flag == 0) { /* 忙等 */ }
    // 期望：能走到这里时 data 一定是 42
    printf("data = %d\n", data);  // 实际可能打印 0
    return NULL;
}

int main(void) {
    pthread_t t1, t2;
    pthread_create(&t1, NULL, writer, NULL);
    pthread_create(&t2, NULL, reader, NULL);
    pthread_join(t1, NULL);
    pthread_join(t2, NULL);
    return 0;
}
```

按源码意图，时间线应是：

```text
写线程:  data=42  →  flag=1
读线程:           看到 flag==1  →  读 data（应为 42）
```

但编译器或 CPU 可能把写线程里两条无关的写重排：

```text
写线程实际可能:  flag=1  →  data=42
读线程:         看到 flag==1  →  读 data（仍是 0）→ 打印 0
```

读线程也可能把 `flag` 缓存在寄存器里，循环里一直读旧值（看起来像「永远等不到」），这同样是缺少同步、优化合法改写可见行为的结果。

> 要点：单线程下 as-if 保证「看起来」顺序没问题；多线程共享普通变量时，源码书写顺序 ≠ 其它线程观察到的顺序。正确做法是用 `atomic`、锁或内存屏障建立同步关系。

### as-if-serial 规则

**as-if-serial（看起来像串行执行）**：无论编译器、CPU 如何重排，**单线程内**的执行结果必须与按源码顺序串行执行时一致。

- 有依赖的指令不能乱序到破坏结果（如 `a = 1; b = a;` 不能变成先用旧 `a` 赋给 `b`）。
- 无依赖的指令可以重排，只要本线程最终结果不变。
- 保证的是**本线程视角**；其它线程仍可能看到中间的乱序状态（见上节多线程例子）。

这也是前面说的 as-if 约束在「指令顺序」上的具体说法：对单线程「看起来」像没重排过。
