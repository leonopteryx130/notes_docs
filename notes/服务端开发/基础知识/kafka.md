# kafka

### 概述

Kafka 作为一个集群运行在一个或多个服务器上，这些服务器可以跨多个机房，所以说 Kafka 是**分布式的发布订阅消息队列系统**。

常用来做：日志收集、流式处理、系统解耦、削峰填谷等。

> 上图每个 Broker 里标的 Partition，实际是该分区的 **Leader** 所在位置（读写都走 Leader）；图上没画出 Follower 副本。

- **Broker**：Kafka 集群中的一台服务器节点。集群由多个 Broker 组成，负责接收、存储并转发消息；Broker 之间可互为备份，提高可用性。
- **Topic**：消息的逻辑分类（主题）。生产者往某个 Topic 发消息，消费者按 Topic 订阅；一条 Topic 下的消息通常会再拆成多个 Partition。
- **Partition（分区）**：Topic 的物理分片。同一 Topic 可有多个分区，分布在不同 Broker 上，实现并行读写与水平扩展；分区内消息有序，分区之间不保证全局有序。每个分区有一个 **Leader** 和若干 **Follower**（副本），客户端只与 Leader 交互。
- **Producer（生产者）**：向指定 Topic 发送消息；可指定分区，或按 key / 轮询等策略决定写入哪个分区。
- **Consumer（消费者）**：从 Topic 拉取并处理消息。
- **Consumer Group（消费组）**：多个消费者组成一组，共同消费某个 Topic。组内对同一分区只有一个消费者在读（竞争消费 ≈ 队列）；不同组各自独立消费同一 Topic（广播 ≈ 发布订阅）。
- **Offset（偏移量）**：分区内消息的序号，消费者用它记录「读到哪了」，便于断点续传。
- **Replica（副本）**：分区在多个 Broker 上的备份（图上未画出）。其中一个是 Leader 负责读写，其余是 Follower 做同步；Leader 挂了可从 ISR 中选举新 Leader，保证高可用。
- **ISR（In-Sync Replicas）**：与 Leader 保持同步的副本集合（含 Leader 自身）。Follower 追赶太慢或宕机会被踢出 ISR；只有 ISR 内的副本才有资格被选为新 Leader。生产者 `acks=all` 时，需 ISR 全部确认写入才算成功，兼顾可靠与可用。

### 什么时候需要用到消息队列系统？

不是凡是服务间调用都要上 MQ。出现下面这些诉求时，引入消息队列往往更合适：

1. **异步解耦**：调用方只关心「事情已受理」，不关心下游谁处理、怎么处理。例如下单后发短信、记积分、通知库存——用同步 RPC 串一串会把系统绑死；丢进队列，各系统独立消费。
2. **削峰填谷**：瞬时流量远高于下游处理能力（秒杀、大促、突发写入）。队列先把请求接住、慢慢消化，避免把数据库 / 下游服务打挂。
3. **广播 / 多订阅**：同一事件要被多个系统同时感知（缓存失效、配置变更、订单状态变更）。MQ 的发布订阅天然适合「一发多收」。
4. **最终一致性**：跨服务不好做强一致事务时，用「本地事务 + 发消息」推动下游补偿/更新，换取可用性和扩展性。
5. **日志 / 事件流**：大量日志、埋点、审计数据需要先缓冲再落库或做流式分析；Kafka 这类高吞吐队列很常见。

**不太适合硬上 MQ 的情况：** 强实时、强一致的请求–响应链路（查库存立刻返回、支付结果必须同步确认等）；引入 MQ 会增加延迟、运维成本和排查复杂度，收益不明显就别用。
